# Maintainer metrics and evidence log

RabbitLens values evidence of useful maintenance over vanity metrics. Do not
create artificial issues, pull requests, stars, forks, or testimonials.

## Monthly maintainer log

At the end of each month, record the totals below in a GitHub issue or release
note. Use real work only.

| Metric | What to record | Why it matters |
| --- | --- | --- |
| Triage time | Hours spent reproducing, labeling, and responding to reports | Shows incoming support workload |
| Review time | Hours spent reviewing and testing pull requests | Shows contributor-maintenance workload |
| Release time | Hours spent building, validating, documenting, and publishing a release | Shows delivery workload |
| Security time | Hours spent auditing dependencies, handling reports, and validating fixes | Shows responsible maintenance |
| Operator feedback | Count of consented trials/testimonials, linked to public evidence when possible | Shows real-world value without inflating metrics |
| Compatibility checks | RabbitMQ versions/plugins tested and linked results | Shows integration maturity |

## Lightweight workflow

1. Use one pinned GitHub issue per month called `Maintainer log: YYYY-MM`.
2. Add time in 15-minute increments with a short link to the PR, issue, run, or
   release that caused it.
3. Ask trial operators for permission before naming them or publishing a quote.
4. Publish only aggregate, non-sensitive operational results.

This log produces accurate material for future grant, sponsorship, and Codex
for OSS applications while keeping the process to a few minutes per week.
